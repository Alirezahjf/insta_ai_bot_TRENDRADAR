# 🧯 چرا ربات بعد از مدتی «Terminated» می‌شود و استپ می‌کند؟

## ✅ خلاصه در یک خط

> **«Terminated» کار پایتون نیست؛ پیام شل لینوکس است وقتی یک عامل بیرونی به پروسه `SIGTERM` می‌فرستد.**
> کد شما هیچ‌جای خودش `exit` یا `terminate` ندارد، پس ربات خودش نمی‌میرد — **از بیرون کشته می‌شود.**
> ریشه‌ی اصلی هم تقریباً همیشه این است: ربات را داخل یک ترمینال SSH به‌صورت foreground اجرا می‌کنی،
> پس زنده‌بودنش وابسته به زنده‌بودن آن سشن است.

---

# 🔬 مرحله‌ی دوم: شواهد سرور خودت (۱۱ اکتبر) — چه چیزی رد شد، چه چیزی ماند

خروجی‌هایی که فرستادی چند تا احتمال را **قطعاً رد می‌کند**:

| بررسی | داده‌ی تو | نتیجه |
|---|---|---|
| **کمبود رم (OOM)** | `Mem: 7940 total / 2176 used / **5764 available**` و `Swap: 0 used` | ❌ **رد شد.** با ۵.۷ گیگ رم آزاد هیچ OOMی رخ نمی‌دهد. ربات هم فقط ۷۰ مگ رم گرفته. |
| **بار/CPU سرور** | `load average: 0.10, 0.11, 0.10` | ❌ **رد شد.** سرور تقریباً بیکار است. |
| **ری‌استارت سرور** | `up 19 days, 23:39` | ❌ **رد شد.** سرور ۲۰ روز است بالا مانده. |
| **خروج کد از خودش** | در کد هیچ `exit`/`sys.exit`ی نیست | ❌ **رد شد.** |
| **خطوط CRON** | `pam_unix(cron:session): session closed` هر ۱۰ دقیقه | ℹ️ **نویز عادی است.** این فقط باز/بسته شدن سشن کرون است، هیچ ربطی به کشتن ربات ندارد. |

و این دو شاهد **دقیقاً می‌گوید مشکل چیست**:

### 🎯 شاهد اول: `last` — سشن‌های SSH تو عمر بسیار کوتاهی دارند

از ۲۰ لاگین آخر تو:

| مدت سشن | تعداد |
|---|---|
| ۰ تا ۲ دقیقه | **۹ تا (۴۵٪)** |
| کمتر از ۱۵ دقیقه | ۱۵ تا (۷۵٪) |
| بیش از ۳۰ دقیقه | ۴ تا |

مثال‌ها: `Oct 10 11:38 - 11:39 (00:01)` ، `Oct 06 10:33 - 10:34 (00:00)` ، `Sep 29 17:47 - 17:48 (00:00)`
و در ۱ اکتبر **۱۰ بار** لاگین/لاگ‌اوت پشت‌سرهم از IPهای مختلف.

📌 **یعنی خط/کانکشن تو مرتب قطع و وصل می‌شود.** (نکته: IP تو هم هر بار عوض می‌شود — `5.126.x`, `91.107.x`, `195.26.x` — یعنی روی موبایل/VPN.)

هر بار که سشن SSH قطع شود، systemd-logind اسکوپ آن سشن را stop می‌کند و **SIGTERM** به همه‌ی پروسه‌های آن می‌فرستد →
عالی‌جناب `Terminated`. 💀

### 🎯 شاهد دوم: پروسه‌ی ۱۰ اکتبر هنوز زنده است — چون از ترمینال جدا شده

در `ps aux` تو این خط هست:

```
root  1275463  0.2  0.8  143604  70896  ?  Sl  Oct10  4:22  python3 bot.py
```

- `?` در ستون TTY = **به هیچ ترمینالی وصل نیست** → برای همین از ۱۰ اکتبر تا الان (بیش از یک روز) زنده مانده، در حالی که در همین بازه چندین سشن SSH باز و بسته شده.
- این عملاً **اثبات تجربی** حرف من است: **ترمینال‌دار = می‌میرد / ترمینال‌ندار = زنده می‌ماند.**

> ⚠️ **قبل از نصب سرویس، این را چک کن:** اگر آن پروسه (PID یا هر `python3 bot.py` دیگری) همان ربات اینستاگرام است،
> اول باید کشته شود وگرنه **دو نسخه** همزمان به یک توکن تلگرام poll می‌زنند → خطای `409 Conflict`، پیام‌های گم‌شده و رفتار دیوانه‌وار.
>
> ```bash
> # این پروسه مال کدام پوشه است؟  (--verbose را حذف کن)
> ls -l /proc/1275463/cwd
> tr '\0' ' ' < /proc/1275463/cmdline ; echo
>
> # اگه مال ربات اینستاگرام بود، ببندش:
> kill 1275463
> pkill -f "python3 bot.py"        # مطمئن شو همه بسته شده
> ps aux | grep "[b]ot.py"         # باید خالی باشه
> # بعد سرویس را نصب کن (پایین ↓)
> ```

## 🔬 چرا مطمئنم؟ (تست‌شده روی همین سرور)

خروجی واقعی تست روی لینوکس:

| سیگنالی که پروسه می‌گیرد | پیامی که شل چاپ می‌کند | کد خروج |
|---|---|---|
| `SIGTERM` (۱۵) | **Terminated** | ۱۴۳ |
| `SIGKILL` (۹) | Killed | ۱۳۷ |
| `SIGHUP` (۱) | Hangup | ۱۲۹ |
| `SIGINT` (۲) | Interrupt / Ctrl+C | ۱۳۰ |

پس پیام شما = **SIGTERM**. دو نتیجه‌ی مهم:

- 🚫 **باگ کد نیست.** اگر کد خطا داشت، یک `Traceback` با شماره‌ی خط می‌دیدی، نه «Terminated».
- 🚫 **به احتمال زیاد مشکل RAM هم نیست.** کشته‌شدن با OOM در لینوکس معمولاً پیام **Killed** می‌دهد، نه Terminated. (برای اطمینان چک‌لیست پایین را بزن.)

---

## 🎯 کی SIGTERM می‌فرستد؟ (به ترتیب احتمال در سرور شما)

| # | عامل | نشانه |
|---|---|---|
| ۱ | **قطع‌شدن / تایم‌اوت‌شدن سشن SSH** (خوابیدن لپ‌تاپ، قطع اینترنت، بستن پنجره‌ی ترمینال، `ClientAliveInterval` در sshd) → systemd-logind کل اسکوپ سشن را stop می‌کند و اول SIGTERM می‌فرستد | رایج‌ترین |
| ۲ | **پنل/هاستینگ** (بعضی سرورها و کانتینرها پروسه‌های طولانی‌مدت را خودکار kill می‌کنند) | دقیقاً بعد از یک بازه‌ی ثابت تکرار می‌شود |
| ۳ | **اجرای دوباره یا `pkill python`** توسط خودت/کرو/تب دیگری | در `ps` دو نسخه دیده می‌شود |
| ۴ | **بروزرسانی سیستم** یا ریستارت سرویس‌ها | سر ساعت خاص |
| ۵ | **OOM (کمبود رم)** — ولی این معمولاً «Killed» است نه «Terminated» | در `dmesg` خط `Killed process ... (python)` دیده می‌شود |

> ⚠️ نکته‌ی کلیدی: **زمانی که ربات foreground در SSH اجرا می‌شود، سشن SSH مالک عمر آن است.**
> بستن ترمینال، خواب رفتن لپ‌تاپ یا حتی یک قطعی کوتاه اینترنت = مرگ ربات.

## 🩺 چک‌لیست تشخیص (روی سرور خودت بزن)

```bash
# ۱) آیا OOM بوده؟ (اگر خروجی خالی بود → مشکل رم نبوده)
dmesg -T | grep -iE "killed process|out of memory"

# ۲) چه چیزی در سیستم چیزی را kill کرده؟
journalctl -b --no-pager | grep -iE "terminated|session .*closed|removed session" | tail -30

# ۳) سابقه‌ی سشن‌های SSH (ببین دقیقاً کی قطع شده)
last -n 20 ; who -a

# ۴) پروسه‌های تکراری ربات (باید ۱ باشد — بیشتر از ۱ = خطای ۴۰۹ تلگرام)
ps aux | grep "[b]ot.py"

# ۵) وضعیت منابع سرور
uptime ; free -m ; df -h /
```

## 🛠 راه‌حل قطعی: ربات را از ترمینال بیرون بیاور و سرویس کن

### گزینه‌ی A — systemd (بهترین راه، توصیه می‌شود) ⭐

**ساده‌ترین کار: اسکریپت آماده را اجرا کن.**

```bash
cd /root/Desktop/insta_ai_bot
chmod +x install_service.sh
./install_service.sh          # اگه فقط می‌خوای ببینی چیکار می‌کنه: ./install_service.sh --dry-run
```

همین. ✋ (مسیرها را خودش پیدا می‌کند، نسخه‌های تکراری را می‌بندد، سرویس را می‌سازد و فعال می‌کند.)

---

اگه ترجیح می‌دهی دستی انجام بدهی:

سرویس `deploy/insta-ai-bot.service` را در این پروژه برایت آماده کردم.
با این کار **هر باری که پروسه به هر دلیلی بمیرد، ۱۰ ثانیه بعد خودکار بالا می‌آید** و اگر سرور ری‌استارت شود هم خودش شروع می‌شود.

```bash
# ۱) فایل سرویس را در جای درست بگذار
nano /etc/systemd/system/insta-ai-bot.service     # محتوای deploy/insta-ai-bot.service را کپی کن

# ۲) ⚠️ دو خط مسیر را با مسیر واقعی پروژه‌ی خودت تنظیم کن:
#    WorkingDirectory= و ExecStart=
#    (پایتون venv خودت را بده: /root/Desktop/insta_ai_bot/venv/bin/python)

# ۳) فعال‌سازی
systemctl daemon-reload
systemctl enable --now insta-ai-bot

# ۴) وضعیت و لاگ زنده
systemctl status insta-ai-bot
journalctl -u insta-ai-bot -f
```

از این به بعد:
```bash
systemctl restart insta-ai-bot     # ری‌استارت
systemctl stop insta-ai-bot        # توقف
```

> ✅ **دیگر لازم نیست ترمینال باز بماند.** SSH را ببند، برو، برگرد — ربات سر جایش است.

## 🔧 اصلاحات کدی که در همین نسخه انجام دادم

### ۱. 🌡 لاگ‌گیری کامل (`bot.log`) — تا دفعه‌ی بعد **دقیقاً** بفهمی چه شد
- هر شروع/پایان و هر سیگنالی که برسد، با تاریخ و ساعت در `bot.log` ثبت می‌شود:
  ```
  2026-10-12 14:31:07 | WARNING | ⛔ سیگنال SIGTERM دریافت شد → پروسه داره بسته میشه (عامل بیرونی)
  ```
  اگر بعد از مرگ این خط بود → عامل بیرونی. اگر نبود → پروسه با `SIGKILL` (مثلاً OOM) کشته شده.
- **heartbeat هر ۳۰ دقیقه** با مصرف رم و تعداد تردها:
  ```
  2026-10-12 15:01:07 | INFO | 💓 heartbeat | age=30 min | RAM=78 MB | threads=21
  ```
  اگر `RAM` مدام بالا برود → نشت حافظه داری (این‌جا نبود، ولی پایش می‌شود).

### ۲. 🧵 رفع یک باگ واقعی که ربات را «قفل» می‌کرد ← مهم
در `core.py`، کتابخانه‌ی `pyTelegramBotAPI` به‌صورت پیش‌فرض فقط **۲ ترد** برای پردازش پیام‌ها می‌سازد.
اما اسکرپ Apify برای هر هشتگ **چند دقیقه** طول می‌کشد و هندلرها همان‌جا **سینک** اجرا می‌شوند؛
یعنی هر اسکرپ فوری، یکی از آن ۲ ترد را دقیقه‌ها قفل می‌کند. با ۲ درخواست همزمان، ربات **جواب هیچ پیامی را نمی‌دهد**
و بنظر «استپ» می‌آید (درحالی‌که پروسه زنده است!).

```python
# قبل:
bot = telebot.TeleBot(config.TELEGRAM_BOT_TOKEN, parse_mode="HTML")
# بعد:
bot = telebot.TeleBot(config.TELEGRAM_BOT_TOKEN, parse_mode="HTML", num_threads=16)
```
✅ تست شد و مقدار ۱۶ درست اعمال می‌شود.

## ⚠️ دو نکته‌ی دیگر که خوب است بدانی

**۱. اگر ربات در لحظه‌ی مقرر خاموش باشد، آن اجرا برای همیشه از دست می‌رود.**
منطق اسکژولر `jobs.py` این است که فقط در همان دقیقه‌ی مقرر چک می‌کند:
```python
if hm in (s["times"] or []):
```
هیچ «جبران اجرای ازدست‌رفته» ندارد. یعنی اگر ربات ساعت ۱۰:۱۲ بمیرد و ساعت ۱۰:۱۳ اسکژول داشته باشی،
آن اجرا کنسل می‌شود. (این را عوض نکردم چون رفتار سیستم را تغییر می‌دهد — بگو تا اضافه کنم.)

**۲. امنیت:** `ADMIN_IDS` در `.env` خالی است و کد در این حالت **همه را مجاز می‌کند**:
```python
def is_allowed(user_id):
    if not config.ADMIN_IDS:
        return True   # ← هر کسی می‌تواند استفاده کند!
```
آیدی عددی خودت را در `ADMIN_IDS` بگذار تا فقط خودت دسترسی داشته باشی.
